# PA 项目 AI Coding 工作流

## 目标

本流程供 Claude Code、Codex 和开发者共同使用，通过结构化上下文、人工审批、原子任务、TDD 和验证门禁，提高 AI 代码采纳率及变更可追溯性。

## 基本原则

- AI 负责检索、分析、计划、实现和验证；开发者负责需求边界、方案审批、破坏性决策和最终验收。
- 先明确“做什么、怎样算完成”，再决定“怎么改”。
- 每次只执行一个可独立验证、可独立回退的原子任务。
- 所有完成结论必须有测试、构建或检查结果作为证据。
- 同一份事实只维护一个权威来源，其他文档只引用，不复制。

## 流程分级

收到任务后，先判断使用快速路径还是标准路径。用户可以明确要求升级为标准路径；执行中发现隐藏复杂度时必须立即升级。

### 快速路径

只有同时满足以下条件才能使用：

- 修改范围小，通常不超过两个文件。
- 需求和验收标准清楚，没有关键歧义。
- 不改变公共 API、数据库结构或模块边界。
- 不新增、删除或升级依赖。
- 不涉及安全、权限、并发、资金、核心状态机或破坏性操作。
- 可以通过局部测试或明确检查独立验证。

执行步骤：

1. 读取相关工程规则、代码和测试。
2. 在对话中说明简短方案和验证方式。
3. 获得用户确认后实施修改。
4. 运行局部测试并检查 Git diff。
5. 报告修改内容、验证结果和剩余风险。

快速路径不强制创建 Issue 目录、`spec.md`、`plan.md` 或 `verification.md`。Bug 修复仍必须先添加能够复现问题的回归测试。

### 标准路径

出现以下任一情况时使用完整流程：

- 新功能、跨模块行为变化或复杂重构。
- 修改公共 API、数据库、依赖或架构边界。
- 涉及安全、权限、并发、资金、LLM 工作流或核心状态机。
- 需求存在重要歧义，或需要多个原子任务。
- 快速路径实施中发现影响范围超出预期。

标准路径执行下述需求澄清、任务规划、TDD、自动验证、AI Code Review 和人工验收阶段，并将产物集中保存在对应 Issue 目录中。

## 阶段一：需求澄清与设计

使用 `superpowers:brainstorming`。

1. 检查现有代码、测试、Wiki 和历史 Issue。
2. 明确业务目标、范围、非目标、边界和异常场景。
3. 使用 Given-When-Then 描述可验收场景，并标记关键优先级。
4. 分析影响模块、数据流、兼容性、监控和回滚。
5. 将批准后的内容写入 `docs/issues/<issue>/spec.md`。
6. 未获批准前不修改实现代码。

## 阶段二：任务规划

使用 `superpowers:writing-plans`。

1. 从已批准的 `spec.md` 拆出原子任务。
2. 每个任务明确修改文件、测试文件、RED 失败点、GREEN 最小实现和验证命令。
3. 任务必须可独立评审和回退。
4. 将计划写入同一 Issue 的 `plan.md`，经确认后开始实施。

## 阶段三：TDD 实施

使用 `superpowers:test-driven-development`。

1. RED：先写目标行为测试，并确认它因功能缺失而失败。
2. GREEN：编写使测试通过的最小实现。
3. REFACTOR：在测试保护下整理结构，不扩大需求范围。
4. 运行局部测试并检查差异。
5. 更新 `plan.md` 的任务状态，再进入下一任务。

出现异常时使用 `superpowers:systematic-debugging`，先复现和定位根因，再修改代码。

## 阶段四：自动验证

使用 `superpowers:verification-before-completion`。

至少检查：

- Spec 中的验收场景都有对应测试。
- 局部测试和相关回归测试通过。
- 后端、前端全量测试通过。
- 前端类型检查和生产构建通过。
- 数据库、外部依赖和失败路径满足安全要求。

验证命令、结果和未执行项写入 `verification.md`。验证失败时不得进入 Review。

## 阶段五：AI Code Review

重要变更使用 `superpowers:requesting-code-review`。Reviewer 必须读取：

- `spec.md`：确认需求、范围和验收场景。
- `plan.md`：确认已批准的任务和变更边界。
- Git diff：检查实际修改和是否越界。
- 测试与构建结果：检查验证证据是否充分。

Review 至少覆盖：

- 需求实现是否完整，BDD 场景是否有对应测试。
- 业务逻辑、边界条件、异常路径和状态终态是否正确。
- 模块边界、依赖方向、API 契约和数据一致性是否被破坏。
- 是否存在安全、隐私、性能或破坏性操作风险。
- 是否出现无关修改、重复实现、不必要抽象或新增依赖。

问题统一分级：

- `Blocker`：安全、数据损坏或核心正确性问题，必须修复。
- `Major`：需求遗漏、架构破坏或关键测试缺失，必须修复。
- `Minor`：局部可维护性或非关键质量问题，建议修复。
- `Suggestion`：不阻断交付的改进建议。

处理 Review 意见时使用 `superpowers:receiving-code-review`，先验证意见是否适用于当前实现。`Blocker` 或 `Major` 未关闭时 Review 不通过；修复后必须重新运行相关验证并复审。Review 结论写入 `verification.md`。

失败必须回退到具体阶段：需求问题回到 `spec.md`，设计问题回到技术方案，实现问题回到 TDD。

## 阶段六：人工 Review、验收与复盘

1. 开发者对照 `spec.md`、Git diff 和 `verification.md` 审核业务意图、风险及 AI Review 结论。
2. 开发者决定接受、要求返工或终止本次变更。
3. 只有人工验收通过，才能进入提交、合并或发布决策。
4. 记录返工原因、门禁失败点和遗留风险。
5. 将可复用的项目事实更新到 `docs/wiki/`。
6. 只有用户明确要求时才提交、推送或创建 PR。

## Issue 产物

```text
docs/issues/<issue-id>-<slug>/
├── spec.md
├── plan.md
└── verification.md
```

文件按阶段创建，不预先创建空文件。需求变化先更新并重新审批 `spec.md`；执行进度只记录在 `plan.md`；验证证据只记录在 `verification.md`。

## 常用验证命令

```bash
make backend-test
make frontend-test
make test
make build
```
