# 可观测性与 Trace 规则

## 适用范围

适用于 API、异步任务、外部服务、数据库、LLM 调用以及需要跨模块排查的业务流程。

## Trace 设计

- 新功能设计时必须说明 Trace 如何产生、跨层传递和结束。
- 每次请求或任务使用同一个 `trace_id` 串联完整调用链；进入异步任务时继续传递，不得重新生成并割裂链路。
- 同时记录已有业务标识，例如 `task_id`、`run_id`；业务标识不能代替 `trace_id`。
- 前端请求、后端 API、任务执行、数据库或外部服务调用应在可控制的边界传递 Trace 标识。
- 本规则不强制引入新的追踪平台或依赖；优先复用项目现有日志与上下文传递机制。

## 日志要求

- 关键节点记录结构化日志：事件名称、`trace_id`、业务标识、状态和必要上下文。
- 调用结束时记录结果状态和耗时；异常时记录异常类型、消息和完整堆栈。
- 字段名保持稳定，禁止把关键标识仅拼接在自由文本中。
- 不记录密钥、Token、Cookie、完整提示词、完整请求正文和其他敏感信息。

## 验收要求

- 能通过一个 `trace_id` 按时间顺序还原关键调用路径。
- 能关联对应的 `task_id` 或 `run_id`，并识别失败发生在哪个组件边界。
- 新增跨组件流程时，测试或运行证据必须覆盖 Trace 标识的生成、传递和异常日志。
