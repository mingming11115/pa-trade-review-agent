# 统一行情定时采集与归档补数

状态：已确认、已实施并通过本机验收；详见 verification.md。

## 用户目标

将本次 MES、MNQ、MGC 历史归档的增量更新写入项目代码，与原有 ES、NQ 分钟行情采集合为一套调度、配置、补数和运行记录。所有历史与新增分钟线统一写入 PostgreSQL 的 `market_archive_2023.bars`，不压缩，不重新下载已保存的 2023 年以来历史数据。迁移原有 `public.market_bars` 的有效数据并切换全部读写后移除旧表。

## 已核实的现状

- `MinuteCollector` 随 FastAPI 启动，在进程内约每 60 秒执行一轮 ES、NQ 采集，然后评估已有告警。
- `public.market_bars` 保存项目使用的分钟和小时行情；MES、MNQ 在现有图表查询中映射到 ES、NQ。
- 真正的 MES、MNQ、MGC 连续近月行情位于同一个 `pa` 数据库的 `market_archive_2023.bars`，共 3,297,965 条，查询视图为 `market_archive_2023.minute_bars`。
- 归档覆盖至 2026-09-30 15:30 UTC（不含结束时刻），保留实际 `instrument_id`、整数价格和纳秒时间。
- `CollectionState` 已记录采集状态；`ScheduledJobRun` 已存在，但当前分钟采集没有按轮次使用它保存执行终态。
- 仓库已有其他功能的未提交修改。实施只修改本 Issue 必需的部分，不覆盖那些修改。

## 推荐方案与替代方案

推荐扩展现有分钟采集流程：统一安排 ES、NQ、MES、MNQ、MGC，所有目标写入同一真实合约归档表，共享上游 HTTP 客户端、异常处理和状态管理。

单独增加归档脚本并配置另一套 cron 容易造成重复采集、状态割裂，不符合合并要求。按用户明确要求，本 Issue 包含统一存储、旧数据迁移和全部行情读写切换。

## 调度与运行方式

- 每 60 秒一轮，只请求已收盘分钟；频率通过配置调整，所有时间窗口与调度槽使用 UTC。
- 同一份业务逻辑提供后端内嵌入口、独立 worker 入口以及 `--once` 手动执行入口。
- 推荐本机独立 worker，由 launchd 在用户登录后自动启动、异常退出后重启；后端启动时可切换为使用外部 worker，避免另启独立循环。
- 仍支持现有“仅后端启动时采集”的部署方式。本机默认采用独立 worker；两个入口均使用同一实现。
- 后台服务不依赖 PA 前端或 FastAPI 运行；电脑关机、退出登录或睡眠期间无法采集，恢复后通过持久化游标补缺。
- 使用 PostgreSQL advisory lock 和持久化调度槽防止多进程或多个入口重复执行同一轮。
- 复用现有告警评估逻辑，每轮只评估一次；单个采集目标失败不阻断其他目标。

## 数据与合约语义

- ES、NQ 新采集也采用 `.c.0` 连续近月并保存真实合约 ID，与三个归档品种共用 `market_archive_2023.bars`。小时及其他周期从统一分钟线聚合，保持 OHLCV 和收盘边界语义。
- MES、MNQ、MGC 使用 `GLBX.MDP3`、`ohlcv-1m`、`stype_in=continuous`，分别请求 `MES.c.0`、`MNQ.c.0`、`MGC.c.0`。
- `c.0` 按到期日排序，不是按成交量选择主力，也不是复权价格。
- 新归档记录直接写入 `market_archive_2023.bars`，按品种、纳秒时间、实际合约 ID 幂等更新；保留原始整数价格、成交量和 UTC 时间。
- 微型合约归档不得通过现有 MES→ES、MNQ→NQ 别名路径获取或落库。
- 原有历史归档保留。项目图表、分析、回填、告警及可选实时成交聚合的读写全部切换到统一存储，MES/MNQ 查询各自真实合约，不再别名到 ES/NQ。
- 迁移前保存旧表可恢复备份，按品种、周期、时间核对。旧表缺少 instrument_id 时必须保留来源并明确标记未知合约，不能编造真实合约 ID，也不能覆盖已有真实记录。旧小时线仅在可由分钟线重建并核对时去重，否则保留独立迁移记录供兼容查询。
- 只有迁移核对与全部读写切换通过后才删除 `public.market_bars`；启动建表不得重新创建旧表。保留现有归档视图与只读用户权限。

## 配置、补数与一致性

- 复用 `DATABASE_URL`、`HIST_BASE_URL`、`HIST_API_KEY`、`COLLECTOR_ENABLED`、lookback 和最大追赶跨度配置；统一采集品种白名单扩展到上述五个品种。
- 增加运行方式与轮询间隔配置，不引入新的任务调度库或行情 SDK。
- 归档初始游标优先取已保存的覆盖截止时间，避免从 2023 年重新下载；缺少归档元数据时才使用可靠的已存数据边界或首次采集窗口。
- 持久化“成功覆盖的查询结束时间”，与最后一条成交分钟分开记录。没有成交的合法空窗可以推进覆盖游标，避免 MGC 稀疏月份或休市期间无限回读旧区间。
- 上游数据尚未发布时，保持等待状态，仅推进已确认发布并成功处理的区间；失败、超时和取消均不得跳过待补数据。
- 长时间停机后按已有最大窗口分批追赶；近端 lookback 继续重叠回补，修正已发布数据。
- 数据写入与相应覆盖游标更新在同一事务内提交；重复执行不产生重复记录。
- 对现有状态表的新增字段提供显式、可重复执行的增量迁移；不能仅依靠 `create_all` 更新已有表结构。

## 状态与可观测性

- 每个调度槽及品种产生持久化运行记录，至少保存开始、结束、查询窗口、写入条数、错误码和终态。
- 成功、失败、取消、超时都有可查询终态；进程异常退出遗留的运行记录在恢复时明确标记中断并补数。
- 一轮一个 trace_id，品种任务通过 run_id 关联；复用现有 logging_context，跨上游请求和数据库写入保持可追踪。
- 密钥不写入源码、提交记录、任务详情或日志；只从既有配置读取。
- key 失效时保留已有数据与游标，记录鉴权失败并退避，不把失败当作“没有行情”。
- 现有 `/api/v1/market/status` 返回五个目标的状态，保持已有响应字段；如实施发现契约必须变化，同步类型、调用和测试。

## BDD 验收场景

1. Given 已配置五个品种，When 执行一轮，Then 五个目标由同一调度入口处理，五个品种全部写入统一归档表，小时线从分钟线聚合。
2. Given 已有 2023 年以来历史归档，When 首次启动补数，Then 从已有覆盖截止点附近追赶，不重新下载完整历史。
3. Given 两个采集进程同时启动，When 争用同一轮任务，Then 只有一个有效执行，同一分钟与合约不产生重复行。
4. Given 同一批数据被重复采集，When 再次落库，Then 主键行数不增加，价格精度与合约 ID 保持正确。
5. Given 合法休市或无成交空窗，When 上游确认该区间已发布且查询成功，Then 覆盖游标推进，不伪造分钟线。
6. Given 上游未发布、超时或鉴权失败，When 执行失败，Then 终态与错误可查，未覆盖区间不被跳过，其他目标可继续。
7. Given 写入事务中断，When worker 重启，Then 不存在“游标已推进但数据未提交”的状态，并从安全边界恢复。
8. Given 启用独立 worker，When FastAPI 未启动或重新启动，Then worker 继续采集；锁机制避免重复运行。
9. Given 在边界分钟取消任务，When 服务关闭，Then 取消有持久化记录，后续重启可补缺。
10. Given 重启后补数完成，When 查询归档视图与现有状态接口，Then 新分钟、正确 UTC 时间和五个品种状态可见。
11. Given 旧表存在分钟与小时线，When 执行迁移，Then 旧数据有备份且可核对，不覆盖真实归档记录；失败时旧表保留。
12. Given 迁移成功，When 查询图表、分析、告警或重启服务，Then 均使用统一存储，MES/MNQ 使用真实微型合约，旧表不存在且不被重建。

## 验证与交付

- 先验证 provider 的连续合约参数、原始整数精度、归档幂等写入、窗口计算与游标推进。
- 验证统一调度、互斥、失败终态、取消恢复、空窗和发布延迟。
- 执行相关局部 pytest，再执行 `make backend-test`；若实际改变跨端契约，再执行 `make test` 和 `make build`。
- 通过本机 PostgreSQL 验证真实归档的一轮增量更新、状态记录及查询结果，并检查启动/停止/重启路径。
- 源码、配置说明、启动命令和 launchd 模板进入仓库；机器上的安装路径、密钥与权限配置不提交。
- 验收阶段再创建 `verification.md`，只引用最新实际命令输出，不提前声称通过。

## 范围边界与回滚

本 Issue 合并采集、定时运行及行情存储，包含现有图表和分析的数据访问切换。保留现有 API 响应结构；品种白名单、前端类型和测试随真实合约查询同步更新。

回滚时停止独立 worker、恢复后端内嵌采集配置；新增归档数据和运行状态保留。移除旧表前保留备份；需要回滚时恢复旧表并切回旧读写路径。统一表内已有历史与新增行情不删除。
