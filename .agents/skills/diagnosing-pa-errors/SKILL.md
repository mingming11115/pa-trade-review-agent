# PA 错误诊断

## 核心原则

先形成证据链，再判断根因。默认只诊断；只有用户明确要求“修复”或“修改代码”时，才进入修复阶段。

开始前读取 `AGENTS.md`、`docs/rules/observability.md` 和任务涉及的其他规则。若 `superpowers:systematic-debugging` 可用，必须同时使用。

## 诊断流程

1. **保留原始证据**：记录第一条有效错误、文件、行列号、错误类型、执行命令和环境；不要从长日志的最后一行反推原因。
2. **分类**：判断属于解析/编译、测试、运行时、数据、依赖、环境、网络或性能问题。
3. **最小复现**：运行能稳定触发问题的最小命令。不能复现时，说明缺少什么证据，不猜测修复。
4. **读取上下文**：检查报错位置前后完整的函数或语法块、相关调用方、测试以及 `git diff` 中的最近修改。解析器指向的位置可能只是它无法继续解析的位置。
5. **追踪链路**：存在 `trace_id` 时，按 `trace_id` 聚合日志并按时间排序，再关联 `task_id`、`analysis_id`、`execution_id`。没有 Trace 时，明确记录可观测性缺口。
6. **提出单一假设**：用“根因可能是 X，因为证据 Y”表达，并用最小检查验证。假设失败后回到证据收集，不叠加多个试探性修改。
7. **给出结论**：按下方固定格式输出。未经修复授权，到此停止。
8. **获得修复授权后**：先建立能复现问题的失败测试或检查，再做一个最小修改；运行局部验证、相关回归和项目规定的构建命令。

## 输出格式

- **错误分类**：错误发生在哪个阶段。
- **复现方式**：实际运行的命令与结果；未运行时明确说明。
- **根因结论**：已确认或仍为假设，精确到文件和代码边界。
- **证据**：错误信息、代码上下文、最近差异、Trace 时间线或运行结果。
- **影响范围**：受影响的入口、调用链和数据。
- **最小处理建议**：只处理根因，不捆绑重构。
- **验证方式**：局部测试、相关回归、构建或运行日志。
- **剩余不确定性**：缺失的上下文、日志或无法执行的命令。

## 快速路由

| 现象 | 优先证据 | 最小验证 |
|---|---|---|
| Vite/Babel/TypeScript 解析失败 | 完整语法块、括号边界、最近差异 | 前端构建或原报错命令 |
| pytest/Vitest 失败 | 第一条失败、测试输入、实际与期望 | 单个失败测试 |
| API 或异步任务异常 | `trace_id` 时间线、业务标识、组件边界 | 重放单次请求或任务 |
| 外部服务失败 | 脱敏后的请求元数据、状态码、超时和重试 | 最小连通性或契约检查 |

## 示例：Babel 报错

看到 `Missing catch or finally clause (1042:4)` 且该行是 `try {` 时：

1. 将其分类为解析阶段错误，不能判断为异步调用失败。
2. 读取当前函数的完整范围，确认这个 `try` 后是否存在 `catch`/`finally`。
3. 检查它之前的 `try`、回调和花括号是否闭合，并查看该区域最近差异。
4. 特别检查错误附近是否存在脱离回调的 `event` 引用或无对应开头的 `});`；这些结构错误可能使解析器在 1042 行才停止。
5. 只有构建命令稳定复现且语法边界证据确认后，才能提出补分支或修正括号的具体方案。

## 常见错误

- 只看报错行就补一个空 `catch`。
- 没有复现就声称根因已经确认。
- 同时修改多个可疑位置，无法判断哪个假设成立。
- 只说“测试通过”，不提供实际命令和最新结果。
- 用业务 ID 代替 `trace_id`，导致跨任务或跨组件日志无法串联。
